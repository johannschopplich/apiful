# Migration

What each breaking change asks of you, grouped by how it reaches you: code that no longer does what it did, behavior that changed underneath it, and types that now catch what they let through before.

## From v6 to v7

### Code You Have to Change

#### Regenerate Your Types

Types generated by v6 list the services in `OpenAPISchemaRepository`, which v7 no longer reads, so APIful's own types fail to compile against them – or, where `skipLibCheck` is set, every call compiles, whatever its path. Run [`apiful generate`](/guide/cli) once you have upgraded and commit the result – until you do, [`--check`](/guide/cli#keep-generated-types-current) reports the committed types as stale.

### Behavior That Changed

#### CLI Messages Name the Generated Types

`apiful generate` called its output "OpenAPI types" and now calls it "generated types". A script that matches the messages needs the new wording:

| v6 | v7 |
| --- | --- |
| `OpenAPI types generated in …` | `Generated types written to …` |
| `OpenAPI types are up to date` | `Generated types are up to date` |
| `OpenAPI types are stale – run …` | `Generated types are stale – run …` |
| `No OpenAPI schemas found, skipping generation` | ``No service sets a `schema`, skipping generation`` |

### Renamed and Removed Exports

Only relevant if you call the [type generator](/reference/type-generator) from your own code, type a custom extension with `SchemaPaths`, augment `OpenAPISchemaRepository` by hand, or import `ResolvedTypeDefinitionOptions`:

| v6 | v7 |
| --- | --- |
| `generateDeclarations` | `generateTypes` |
| `GeneratedDeclarations` | `GeneratedTypes` |
| `GenerateDeclarationsOptions` | `GenerateTypesOptions` |
| `generateSchemaTypes` | `generateDocumentTypes` |
| `EMPTY_SCHEMA_TYPES` | `EMPTY_DOCUMENT_TYPES` |
| `SchemaGenerationError` | `GenerationError`, whose `name` is `'GenerationError'` |
| `SchemaPaths` | `ServicePaths` |
| `OpenAPISchemaRepository` | `OpenAPIServiceRepository` |
| `ResolvedTypeDefinitionOptions` | Removed – write `Required<TypeDefinitionOptions>` |

## From v5 to v6

### Code You Have to Change

#### Node 24 and TypeScript 5.9

APIful now requires Node 24 or later, and its types require TypeScript 5.9 or later – see [Install APIful](/guide/getting-started#install-apiful).

#### Regenerate Your Types

APIful generates the types itself now, without openapi-typescript, and the output differs from what v5 wrote. Run [`apiful generate`](/guide/cli) once you have upgraded and commit the result – until you do, [`--check`](/guide/cli#keep-generated-types-current) reports the file as out of date. The [openapi-typescript migration guide](/guide/migrating-from-openapi-typescript#where-the-generated-types-differ) lists every difference from openapi-typescript's output.

Remove `openapi-typescript` and `json-schema-to-typescript-lite` from your dependencies afterwards. APIful loads neither.

#### `OpenAPIBuilder` Is Now `openAPIBuilder`

The extension builder is now spelled like `ofetchBuilder` and `apiRouterBuilder`:

```ts
import {
  createClient,
  OpenAPIBuilder, // [!code --]
  openAPIBuilder, // [!code ++]
} from 'apiful'

const petStore = createClient({ baseURL: 'https://petstore3.swagger.io/api/v3' })
  .with(OpenAPIBuilder<'petStore'>()) // [!code --]
  .with(openAPIBuilder<'petStore'>()) // [!code ++]
```

#### The Configuration Is an ES Module

The CLI imports `apiful.config.{ts,mts,js,mjs}` with Node's native `import()` instead of loading it through c12. What c12 added on top goes with it:

- `.cjs`, `.cts`, `.json`, `.jsonc`, `.json5`, `.yaml`, `.yml`, and `.toml` files are no longer read, and neither is a `.config/` directory. Move the configuration into an `apiful.config.ts` with a default export.
- A default export that is a function is no longer called, and the CLI rejects it. Export the configuration object itself.
- `extends` layers and `$development` or `$production` overrides are gone. Branch on `process.env` in the module instead.
- TypeScript syntax and relative imports follow [Node's rules](/guide/cli#generate) instead.

#### The `openAPITS` Option Is Gone

`openAPITS` passed its settings on to openapi-typescript, which APIful no longer runs, so delete the key, along with the `openAPITSOptions` field of `GenerateOptions`. If you set `rootTypes`, [name your schema types yourself](#name-your-schema-types-yourself) instead.

#### Import From the Remaining Entry Points

Three subpaths are gone, and the type generator moved to a subpath of its own, since it runs on Node.js only:

| v5 | v6 |
| --- | --- |
| `apiful/extensions` | `apiful` |
| `apiful/openapi/client` | `apiful/openapi` |
| `apiful/openapi/types` | `apiful/openapi` |
| Generator exports of `apiful/openapi` | `apiful/openapi/generate` |

The generator exports were renamed on the way – see [Renamed and Removed Exports](#renamed-and-removed-exports-v6).

#### Name Your Schema Types Yourself

Each fragment, `apiful/schema/<service>`, exports `paths` and `components` – plus a `WithRequired` helper where a schema needs one – and nothing else. The named schema types `rootTypes` generated are gone, and so are the `operations`, `webhooks`, and `$defs` types. Declare an alias for each type you use, through the type helpers of the entry, `apiful/schema`:

```ts
import type { PetStore, PetStoreModel } from 'apiful/schema'

// Before: `SchemaPet` from 'apiful/schema/petStore'
export type Pet = PetStoreModel<'Pet'>

// Before: `operations['getPetById']` from 'apiful/schema/petStore'
export type GetPetById = PetStore<'/pet/{petId}', 'get'>['operation']
```

#### HTTP Status Constants Follow RFC 9110

The [status codes](/utilities/http-status-codes) and [phrases](/utilities/http-status-phrases) are generated from the IANA registry now, so five constants take the name RFC 9110 gives their code:

| v5 | v6 |
| --- | --- |
| `MOVED_TEMPORARILY` | `FOUND` |
| `REQUEST_TOO_LONG` | `CONTENT_TOO_LARGE` |
| `REQUEST_URI_TOO_LONG` | `URI_TOO_LONG` |
| `REQUESTED_RANGE_NOT_SATISFIABLE` | `RANGE_NOT_SATISFIABLE` |
| `UNPROCESSABLE_ENTITY` | `UNPROCESSABLE_CONTENT` |

The phrases of these five follow their names, and `NON_AUTHORITATIVE_INFORMATION` reads `'Non-Authoritative Information'`. `IM_A_TEAPOT` (`418`), `INSUFFICIENT_SPACE_ON_RESOURCE` (`419`), and `METHOD_FAILURE` (`420`) are gone, since the registry marks `418` unused and assigns neither `419` nor `420`.

#### Pass JSON Query Parameters as Objects

A query parameter declared with `application/json` content and an object schema used to be typed as `string`, so you serialized it yourself. It is now typed as its schema, and ofetch serializes the object to JSON when it builds the URL. A `JSON.stringify` left in place no longer compiles:

```ts
await catalog('/items', {
  query: {
    filter: JSON.stringify({ name: 'lamp' }), // [!code --]
    filter: { name: 'lamp' }, // [!code ++]
  },
})
```

A JSON parameter with an array or primitive schema stays `string`. An object schema with an empty `properties` admits no keys, as it does anywhere else, so its parameter is `Record<string, never>`. Where a type of your own mirrors a parameter with an object schema as `string`, type it as the object, too.

#### `jsonToTypeDefinition` Returns a String

[`jsonToTypeDefinition`](/utilities/json-to-type-definition) used to return a promise of the definition. Drop the `await` – a `.then()` on the result no longer compiles. The output changed with it: members end in semicolons, and the `/* eslint-disable */` header is gone.

#### The Validation Utilities Are Gone

`apiful/utils` no longer exports `jsonSchema`, `validator`, `validateTypes`, `safeValidateTypes`, `isSchema`, `isValidator`, `validatorSymbol`, `TypeValidationError`, or the types `Schema`, `Validator`, and `ValidationResult`. No part of the client used them. Validate with a dedicated library instead, such as [Ajv](https://ajv.js.org) for JSON Schema.

### Behavior That Changed

#### An Object Body Is Sent as JSON for Every Method

ofetch serializes an object `body` only for `PATCH`, `POST`, `PUT`, and `DELETE`, so v5 sent one on any other method – `QUERY`, `SEARCH`, or a custom method – as `[object Object]`. The OpenAPI client now [serializes it as JSON for every method](/extensions/openapi#send-a-request-body) and sets `content-type` and `accept` to `application/json` where you have not set them. A `JSON.stringify` with a hand-set `content-type` can go:

```ts
await catalog('/items', {
  method: 'QUERY',
  body: JSON.stringify({ name: 'lamp' }), // [!code --]
  headers: { 'content-type': 'application/json' }, // [!code --]
  body: { name: 'lamp' }, // [!code ++]
})
```

#### A `.` or `..` Path Parameter Rejects the Call

A path parameter of `.` or `..` that fills a whole segment used to go out as a dot segment, which resolves the URL to another path. Where such a value can come from user input, handle the `Error` the call now [rejects with](/extensions/openapi#pass-path-parameters) before sending anything.

### Types That Are Now Stricter

These changes touch no runtime behavior. They reach you as compile errors where the old types disagreed with the client or the OpenAPI document.

#### An Unknown Service Name Fails to Compile

A service name missing from your configuration used to type the client against an empty OpenAPI document. Correct the name, or add the service to the configuration and rerun `apiful generate`:

```ts
createOpenAPIClient<'petStroe'>()
//                  ^^^^^^^^^^ v6: does not compile, no service is named `petStroe`
```

#### A Handler Extension Replaces the Previous One

Adding a second handler extension replaced the first at runtime, but the type kept both call signatures – so after `.with(ofetchBuilder()).with(openAPIBuilder<'petStore'>())`, a path the OpenAPI document does not declare still compiled. Such a call fails to compile now. Drop the first handler extension, which never handled a call.

#### Path Items in `paths` Hold Only Their Methods

A generated path item used to list all eight HTTP verbs, setting the undeclared ones to `never`, plus a path-level `parameters` key. It now holds the methods the path declares and nothing else, so indexing a missing one fails:

```ts
import type { paths } from 'apiful/schema/petStore'

type PetMethods = keyof paths['/pet']
//   ^? v5: 'parameters' | 'get' | 'put' | 'post' | 'delete' | 'options' | 'head' | 'patch' | 'trace'
//   ^? v6: 'put' | 'post'
```

Path-level parameters are merged into every operation of the path, as before.

#### Binary Strings Are `Blob | File`

A `format: binary` string, or one with a non-JSON `contentMediaType`, used to be typed as `string`. Pass a `Blob` or a `File` instead – a string no longer compiles.

#### A Multipart Body Is a `FormData`

A `multipart/form-data` request body used to be typed as its schema's object, which ofetch sends as JSON whatever the operation declares. [Build a `FormData`](/extensions/openapi#send-a-request-body) instead – an object no longer compiles.

#### A Form-Encoded Body Widens `request` With `URLSearchParams`

Where an operation accepts an `application/x-www-form-urlencoded` body, `request` also includes `URLSearchParams`, so reading a property off a value typed as `PetStore<'/pet', 'put'>['request']` no longer compiles. Type the value with [`PetStoreModel`](/reference/openapi-type-helpers#schema-model-types), or index `operation` by a media type other than the form-encoded one, such as `application/json`.

#### A Property With a `default` Can Be Missing

A property with a `default` used to be required outside request bodies and parameters. Code reading one from a response handles `undefined` now, unless the schema lists it as `required` – JSON Schema treats `default` as an annotation that promises no value.

#### Every 2xx Status Counts as Success

v5 took `response` and `error` from fixed lists of status codes, which missed `205`, `208`, and `226` among the 2xx statuses and codes such as `419` and `509` among the errors. Both now cover [every status the operation declares](/reference/openapi-type-helpers#core-type-properties) in their range, and so does the `data` a thrown error carries. Code reading either handles the bodies of those statuses now.

#### The Response Follows `responseType`

A call with a `responseType` other than `json` used to be typed as the JSON body from the OpenAPI document, although ofetch hands back something else. It is now [typed as what ofetch returns](/extensions/openapi#type-non-json-responses), so a cast to `Blob` or `string` can go.

#### A Call With Required Options Needs Its Options

The options argument used to be optional on every call, so leaving it out skipped the check of what it has to hold. It is now required wherever the operation [requires an option](/extensions/openapi#call-an-endpoint), such as a path parameter:

```ts
await petStore('/pet/{petId}')
//             ^^^^^^^^^^^^^^ v6: does not compile, `path` is missing
```

### Renamed and Removed Exports {#renamed-and-removed-exports-v6}

Only relevant if you call the generator from your own code or build on the client types. The generator exports now come from `apiful/openapi/generate`, which the [Type Generator](/reference/type-generator) reference covers:

| v5 | v6 |
| --- | --- |
| `generateDTSFragments` | `generateDeclarations` |
| `DTSFragmentOutput` | `GeneratedDeclarations` |
| `GenerateOptions` | `GenerateDeclarationsOptions` |
| `generateDTS`, `joinDTSFragments` | Removed – write `entry` and `fragments` yourself |
| `generateSchemaTypes({ id, service, rootDir })` | `generateSchemaTypes(await loadOpenAPIDocument(schema, { rootDir }))`, synchronous |
| `generateTypeHelpers(id)` | `generateTypeHelpers(serviceName, { paths, components })` |
| `OpenAPI3` from openapi-typescript | `OpenAPIDocument` |
| `createOpenAPIHandler(fetch)` | `createOpenAPIClient({}, { fetch })` |
| `ClientOptions` | `FetchOptions` from ofetch |
| `createClient<BaseURL>()` | `createClient()` |
| `ApiClient<BaseURL>` | `ApiClient<Handler, Methods>`, without `_handler` and `_extensions` |
| `OpenAPIFetchOptions`, `FilterMethods` | Removed |

## From v4 to v5

### Code You Have to Change

#### Extending a Client Returns a New One

`with` used to write the extension into the client you called it on, so throwing its return value away still worked. Each call now leaves its receiver as it was and hands you the extended client, which is the one you have to keep:

```ts
import { createClient, ofetchBuilder } from 'apiful'

const client = createClient({ baseURL: 'https://api.example.com' })
client.with(ofetchBuilder()) // [!code --]
  .with(ofetchBuilder()) // [!code ++]
```

Written as one chain, which is how the documentation has always shown it, nothing changes. Written as separate statements, the client you kept has no handler, and calling it throws.

#### Every Service Needs a `schema`

A service used to be valid without a `schema`, although it had nothing to generate from and was never more than a placeholder. Give every service one, or drop it from the configuration:

```ts
import { defineApifulConfig } from 'apiful/config'

export default defineApifulConfig({
  services: {
    petStore: {
      schema: 'https://petstore3.swagger.io/api/v3/openapi.json',
    },
  },
})
```

A missing `schema` is a type error in a TypeScript configuration file. In a JavaScript or JSON one it surfaces when you run [`apiful generate`](/guide/cli), which names the services it skips and generates the rest.

The `url` option is gone from the same type. Nothing ever read it, so delete the key if you have one.

### Behavior That Changed

#### A Client Without a Handler Throws

Calling a client that has no handler extension used to return `undefined`, which looked like a request that came back empty. The error it throws instead names the fix:

```
TypeError: This client cannot make requests. Add a handler extension, such as `createClient().with(ofetchBuilder())`.
```

Add one of the [built-in extensions](/extensions/), or [write your own](/guide/custom-extensions).

#### An Unreadable OpenAPI Document Fails the Run

The generator used to log an OpenAPI document it could not read or parse and carry on, emitting an empty stub for that service – leaving you with a client that compiled and was silently untyped. The run now stops:

```
Failed to generate types for service `petStore` – …
```

[`apiful generate`](/guide/cli) exits with code `1` and writes no types. Calling the generator from your own code, the same failure arrives as a `SchemaGenerationError`.

### Types That Are Now Stricter

These changes touch no runtime behavior. They reach you as compile errors in code that was already asking for something the OpenAPI document does not offer, and as narrower types where the old ones guessed.

#### The Type Helpers Offer Only the Methods a Path Declares

The type helpers used to offer methods a path does not declare, such as `get` on `/pet`. Naming one now fails to compile:

```ts
import type { PetStore, PetStoreApiMethods } from 'apiful/schema'

type PetMethods = PetStoreApiMethods<'/pet'>
//   ^? v4: 'get' | 'post' | 'put'
//   ^? v5: 'post' | 'put'

type Endpoint = PetStore<'/pet', 'get'>
//              ^^^^^^^^^^^^^^^^^^^^^^ v5: does not compile, the Petstore declares no `get` on `/pet`
```

Where this bites, the OpenAPI document is the place to look: the method you were reaching for is not in it.

#### Request and Response Resolve the Way the Client Does

`request` and `response` used to be hardcoded to `application/json` and to status `200`. They now resolve through the same helpers a call resolves through, so what the type says and what a request hands back cannot drift apart. Three things follow from that:

**A status with no body is `undefined`, not an empty object.**

```ts
type PetNotFound = PetStore<'/pet/{petId}', 'get'>['responses'][404]
//   ^? v4: Record<string, never>
//   ^? v5: undefined
```

**`response` is whichever 2xx status and media type the operation declares**, rather than always `200` and always JSON. It is `undefined` where the 2xx status declares no content, and `never` where the operation declares no 2xx status.

**An optional request body comes back widened with `undefined`**, matching what the client accepts:

```ts
type PlaceOrderBody = PetStore<'/store/order', 'post'>['request']
//   ^? v4: Order
//   ^? v5: Order | undefined
```

Parameters follow the same rule: `path` and `query` are `never` for an operation that declares none, where v4 offered an empty object you could pass around. See [OpenAPI Type Helpers](/reference/openapi-type-helpers) for the full set.

### Renamed Exports

Only relevant if you call the generator from your own code instead of through the CLI:

| v4 | v5 |
| --- | --- |
| `generateDTSModules` | `generateDTSFragments` |
| `joinDTSModules` | `joinDTSFragments` |
| `DTSModuleOutput` | `DTSFragmentOutput` |
| `DTSModuleOutput['modules']` | `DTSFragmentOutput['fragments']` |
